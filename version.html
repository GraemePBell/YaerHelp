YaerZero Version History

Version 2.1.5

Bug Fixes

  • Current book is now always the Most Recent Book loaded when using the Current Book Buttons.

    Sort on Author wasn't working properly.
  • Bug Fixes (the short details)
    The currently displayed book (in the library) is selected based on which control the user had last selected, but it is not necessarily fully loaded. The process of displaying a selected book would set preconditions to alter the current book under certain circumstances, but not others.
    This behaviour is intentional. I use a finite-state machine to determine how the many possible user-interactions map to outputs.
    If the preconditions were met, it would result in me assuming the wrong value for the current book ("top of the Library List"), prior to using the Current Book button. I now force the FSM by passing it "top of the MRU list" and *then* read, rather than assuming correctness. The actual current book is always top of the Most Recently Used list.
    That's a fancy way of saying I made an assumption about a complex set of interactions and I was wrong.

    When removing the Boost library, I introduced a typo resulting in a comparison failure when sorting on Author name.
    Hands up, it was a bad copy-pasta-edit. I duplicated my code to upper-case the names, but forgot to rename the variables. That is not-at-all embarrassing. Don't do this at home, kids. And really, don't do it front of witnesses. There will be (well-deserved) mockery.
    It was discovered in debug mode when the latest stable version of the MSVC build tools asserted with "invalid comparator", while scanning what should have been identical strings in a std::stable_sort.
    I do like well-placed asserts.

Version 2.1.4

Bug Fixes and Performance Improvements

  • Filtering on Comics and PDFs work properly now. PDF names are displayed correctly. Speed up in processing libraries.
  • Bug Fixes
    Filtering the library by Comic and PDF was broken. I had neglected to add a new option after adding the code to do all the work. The engine was there, the gearbox had been upgraded, but the selector didn’t have a slot for the new gear. Oops. It works now.
    YaerZero was displaying the truncated internal name of PDFs, rather than the original name. Sorted now.
  • Performance Improvements
    Moving from the UWP Task based multiprocessing to the WinRT and C++ co-routines model meant that my singleton model for decoding books had been quietly deprecated (and in-practice removed). The UWP version had been firmly On modern, multicore processors, the singleton model left a lot of CPU power sitting idle. With the singleton book-structure decoder now not really singleton, I could allocate a thread to each book, without worrying unduly about internal decompressor state. With WinUI requiring me to manage much more of the details of information flow, it allowed me to reach to the point where each Book Structure Processor was safely self-contained.

With the singleton book-structure decoder now not really singleton, I could allocate a thread to each book, without worrying unduly about internal decompressor state. With WinUI requiring me to manage much more of the details of information flow, it allowed me to reach to the point where my Book Structure Processor was safely self-contained.

    I decided to use a thread-pool of no more than half the available hardware threads or 8, whichever is smaller. I didn’t want to swamp the processor and simultaneously overload RAM. Loading and decompressing being the most memory intensive steps. Depending on feedback, I may throttle based on available RAM as well. We’ll see how it goes.

    A quick test run revealed only one issue, easily solved by replacing explicit memory management. So I removed the explicit calls and let RAII do it’s thing.

    The performance gain is, of course highly dependent on the processor - the greater the number of cores, the better. It is also dependent on the files being processed. A single, large Graphic Novel or Omnibus Collection will not block other items being processed, but it will still dominate the overall processing time. On a large library of small ePubs, the efficiency does get within shouting distance of the theoretical limits. Which is nice. My library of Gutenberg.org top 100 epub2 and epub3 books has dropped from 45 to 20 seconds. The problematic-books suite is now only 65 seconds, down from 95. Not bad, considering the Windows GUI overheads.

Version 2.1.3

Minor Bug Fixes and Improvements

  • Better error reporting for unrecoverable badly formed books.
  • Bug Fixes
    Bug fix for a very, very occasional Obi-Wan. I managed to get it to fail reliably on a rejigged, previously perfectly-decoded file and thereby detect an off-by-one read of a particular sized RAR filter. Thanks to std::span for picking that up in DEBUG mode. It never triggered in the wild, but it could have.

    The Import button could fail to re-enable if the right combination of import failures happened. It was an odd combination, bypassing the re-enable logic, revealed by PDF imports making that case more frequent. Fixed now.

    Removed customisation of the error-reporting dialogs. Frankly, this customisation revealed just how badly broken the default ContentDialog is in WinUI. The dialog responds very differently to customisation depending on the system theme. In light mode, it does exactly as expected, respecting the customisation. In dark mode, it uses the customisation in completely erroneous ways, ignoring all attempts to correct it. The carefully placed image in light mode, completely filled the dialog in dark mode, rendering text unreadable. The buttons went fully transparent and button text was rendered in translucent white. On top of that, it only respected the system theme, not the app theme. It's an absolute mess.
  • Minor Improvements
    YaerZero now better reports what kind of error it has encountered when it cannot open a book. New dialogs have been added to report Drag&Drop issues.

    No more naked throws! There were a couple of throws in exception-using code that did not have appropriate exceptions attached. This was from old, pre-release code, from when I wanted the crashes, so I could fix bugs, rather than recover silently and/or gracefully from external errors. I don't ever expect to see those exceptions. That's why they are exceptions.

    Some more std::spans replacing contiguous memory references and a few allocations. Unlike previous replacements, these were not-so-much speed, as memory optimisations. Memory usage in decompression should be roughly halved, depending on the book being decompressed. Larger Graphic Novels will benefit the most from this, but overall memory usage should be decreased.

    A lot of general tidying - commenting, defensive bracketing and removal of dead code.

Version 2.1.1

Feature Release:

  • Reading of PDF Files is now supported.

Commentary:

  • Feature: Reading PDF files

    This has been on the wishlist since before there was a wishlist. I did look at the PDF format with an eye to decoding and rendering it myself.

    I looked, and while I might do it one day, it is not this day.

    The PDF format is as complex as one might expect given its long history and it's goal of making the paperless-office a reality. It is a very well documented format. However the open-sourced documents run to 230 pages for the obsolete Version 1.0 and there are Versions 1.7 and 2.0. I'd rather read the back of shampoo bottles than read another ISO preamble. Unfair? Probably.

    On top of that, the WebView2 control has a reasonably competent PDF Viewer built in. Therefore, I have used that to integrate PDF reading into YaerZero. Using the built-in "black-box" viewer means a few compromises in the UI, but anyone accustomed to reading PDFs expects certain things out of their reading software and the control provides the typical UI without the need (or indeed ability) to provide it manually.

    The WebView2 PDF control has a few caveats over a "real" PDF viewer. It's a bit slower in loading. It doesn't handle huge, complex PDFs well - over a Gigabyte is probably expecting too much, although it should fail gracefully, not crash. It doesn't handle corrupted PDFs as well as a dedicated reader, but again it should not crash.

  • Code Modernisation

    Coherent handling of unicode strings in the input. Ad-hoc mitigations for characters in the more elevated code points have been replaced by a consistent pipeline that maintains them in wide-character form and only narrowing when, and if, required. There were a few places where unnecessarily premature narrowing was creating more work, and resulted in poorer fidelity.
