Version 2.0.15.0

Minor Code Quality Release.

  • Quality improvements in the Rar Virtual Machine, including removal of raw pointers and use of std::span<uint8_t> for all data buffers.

Commentary:

  • Bug fixes

    Nothing visible to the end user, but a few latent bugs were found and fixed. The code is now more robust and less likely to fail on malformed input.

  • Code Modernisation

    I completed the removal of raw pointers from the Rar Virtual Machine. After that, I checked whether converting to std::span had exposed any latent bounds‑checking issues by running Address Sanitiser over my problematic books test‑suite. ASAN reported exactly one issue: a single filter over a single file in a single book, again inside the Rar VM. Nothing else was flagged.

    The underlying memory access was still within the allocated buffer, but the code was now operating inside a subspan with stricter bounds, and was inadvertently stepping past the end of that block.

    Was it a bug? Not in practice, but it was a potential bug, lying in wait for a malformed input.

    That particular VM filter combined with the particular image would have produced an broken image file, if erroneous data was used, rather than merely accessed, but the image was unpacked and saved without any problems.

    However, although the code was only accessing valid memory, it was doing so in a way that no longer matched the stricter limits I had chosen for the new subspans.

    The fix was to check the number of bytes remaining in the current working std::span and adjust the size of the subspan accordingly.

    A problem with a simple fix, but it was a good test of my code, my use of std::span and proved to me that ASAN was working correctly – the execution-speed penalty is prohibitive when it's enabled. It's nice to know it's doing something valuable when I run it.

    I then ran a full-debug build over my test-suites, to see if it picked up anything the ASAN build didn't. There was another OBI-WAN (Off-By-One, or fencepost) bug, in the adjacent function to the one ASAN had flagged. It is worth noting that I asked Github Copilot about it and it suggesed putting an assert in the failing function. The function that was asserting already.
    *shrug*
    I can't wait for C++26 and the new contracts feature that will let me turn these into compile-time asserts.

    Why not always use debug builds? Because they are slow. I have a large test suite of books and running them all in debug mode takes a lot longer than in release mode. A run over my pathologically-broken books test-suite takes about 3 minutes in release mode, but nearly an hour in debug mode.

    Also, debug is not the same binary as release. Optimisations can (and do!) change a lot of code. It's almost always better to code and test on release builds and check failures in debug.

    Other Changes

    I implemented a banned list of 3rd-party metadata files that sometimes occur in epubs, but cause more hassle than they are worth. Those files are never processed now. The defensive logic, for each of those types can be removed in a later release.

    Early in development, I had generated 8-bit char filenames for the html encapsulated images in graphic novel pages, by using std::filesystem::path as a shortcut. When replacing it with a real std::wstring to std::string function(and later std::u8string), I missed an instance. This could result in very occasionally incorrect characters in (and only in) URIs linking to images with "odd" names. The path uses the system locale to convert wide-characters to 8-bit chars, in this case Win1252 and not UTF-8. Finding the missed call allowed me to simplify and remove a swathe of unnecessary translation and checking code, that had built up around handling special-cases.

Version 2.0.14.0

Minor Bug Fix release.

  • Mitigation for internal files with ampersands in their names causing WebView2 to fail to parse HTML referencing them, even if the filenames were in quoted attributes.

Commentary:

  • Bug fix

    I find it difficult to believe that this had not turned up in my in-the-wild test suite before, but now it has, and so it's an issue. Of course, I could say that it's a malformed book, but since other readers handle it, so must YaerZero. The fix is trivial. I have full control of names and they already go through a sanitisation pass, where I can choose any safe character to replace the ampersand. I went with '+' since it's a valid character in both a URI, and a Windows filename, while also being semantically similar to an ampersand.

  • Code Modernisation

    Unrar unpacking interfaces now almost completely raw-pointer free. std::span almost everywhere, smart pointers where needed with std::array and std::vector used for actual data.

    The only hold-outs are the PPM code and the Virtual Machine for decompression filters. Since the PPM code never seems to get exercised by any of the real-world books I test on, it's not a high priority. The VM code is underway, but as one might expect, it's rather heavy on pointer arithmetic.

Version 2.0.13.0

Minor Bug Fix Release.

  • Fixed a rare crash caused by reporting multiple broken books in a single, extended operation.

Commentary:

  • Bug fix

    The code was correctly handling unrecoverable archive errors, but reporting it via a custom dialog could result in instability, if the first dialog wasn't dismissed quickly enough. Could, but definitely not always. The asynchronous code meant the diagnostics were rarely in the current thread context.

    It proved easy to fix, once I got it to be reproducible - two very broken ePub (ZIP) archives in rapid succession. The code was trying to display a second dialog, while the first was still being handled by the Windows Runtime. According to spec, it should either queue or drop the second dialog and carry on. It wasn't doing either reliably. Probably because of my custom dialog.

    WinUIs handling of MessageDialogs is a bit quirky, requiring a valid and appropriate HWND, which is not always reliably available, so my custom implementation was needed. The fix was to queue and process the dialogs manually.

    Honestly, that blew me away - WinUI uses it's own internal window handles and they don't always have a valid system HWND available, because, I guess, Windows Runtime does it's own thing. This is not documented anywhere I could find. I found out during the initial port from UWP to WinUI by trying to use the WinUI MessageDialog class and having it sporadically fail with "Invalid HWND" errors. Hence the custom dialog and hence the bug.

  • Code Modernisation

    Some other minor improvements involving std::span<uint8_t> replacing raw pointers in more functions. Renaming of some variables to better reflect usage. Removal of redundant code, e.g. 32-bit build checks. Ongoing checks on compiler issues and workarounds.

Version 2.0.12.0

Performance Improvements Release - The Sequel.

  • Even faster and even less memory-heavy. Significant speed gains in both ZIP (ePub and CBZ), and in RAR (CBR) decompression.

Commentary:

  • Code Modernisation

    Applying the lessons learned in the previous release, I have used std::span wherever sensible. I no longer copy or move data buffers around, passing std::span has reduced expensive heap allocations and overall memory usage.

    I'd like to say it's 10x now, and on some books it is, but the average improvement is between 2x and 5x. It is never slower. The most pleasing improvement is on large, illustrated, technical epubs where the time to complete processing has dropped from a full-on coffee-break, to an appreciative sip and a nibble on a biccie.

    C++20/23 gave me these optimisations, without sacrificing safety or the readability of my code. The architecture is still mine, but the code is now more modern, more efficient and more maintainable. I am very pleased with the results.

Version 2.0.11.0

Performance Improvements Release.

  • Generally faster and less memory heavy. The biggest gains are in ePub and CBZ import.

Commentary:

  • Code Modernisation

    Lots of small changes, such as more use of constexpr, std::string_view and improvements in initialisation. Code has been re-ordered to make better use of data locality, cache-efficiency and reduce the chances of pipeline stalls. This results in a general improvement in performance and memory usage.

    The biggest gains are in ePub and CBZ import, where, along with the other changes, the unzip code has been restructured using std::span to avoid making unnecessary copies of data, while remaining safe and robust. The speed gain can be up to 50% and average memory usage is reduced by a similar amount.

    The code is now more readable and maintainable, while also being faster and much more memory efficient.

    These are the kind of changes that I was keen to incorporate into the codebase, but was unable due to UWP being locked to C++17. WinUI C++/WinRT allows me to use the more modern facilities of C++20/23.

Version 2.0.08.0

Minor bug-fix release.

  • Speed, reliability and "quality-of-life" improvements.

Commentary:

  • As a programmer who likes to get down in the weeds, so-to-speak, that kind of utterly uninformative "release notes" is an, admittedly minor, irritation. Stuff changed, nothing I can explain without getting more technical than an average user wants to know.

    I'm not an average user - maybe you're not either.

    Some CSS management fixes, re-organising the code that parses and regularises incoming CSS.

    Continuing to replace std::wstring and local string literals with constexpr std::wstring_view. Likewise, replacing std::vector with constexpr std::array, wherever the size is fixed and known at compile time.

    Fixed a problem with one particular epub that caused the program to hang on thumbnail generation. Still investigating the root cause, but the result was a duplication in the list of thumbnails to be generated and the code was waiting on an image that would never appear. De-duplicated the std::vector, while still trying to figure out why the code would write twice, just for that one book. It's all very strange, but the bodge is in place and the program no longer hangs on that book. The root cause will be found and fixed in a future release.

    Gathered together all the string literals used as file extensions, moved them into a single header file and made them constexpr std::wstring_view. When in the heat of coding it's too easy to type ".jpg" rather than a consistent constant name (wide_JPG_ext, u8_JPG_ext, narrow_JPG_ext, or whatever). Or ".jpg" in one place and ".jpeg" in another, or ".cbz" and ".zip". Or worse, ".jpg" and ".JPG". I found no errors, but now it's all in one place and consistent.

    Fixed an edge-case in content page handling, where the old content page from a previous book was being held and overwriting the new value. It required a series of steps to reproduce that was very rare in the UWP version (effectively unreproducible because UWP just does the right thing when marshalling data across the ABI), but it became slightly more likely in the WinUI version where I have to mimic the UWP marshalling behaviour.

    Handled the fallback case of a missing cover image. This was a solved problem in the EdgeHTML version, but WebView2 is a bit more awkward about HTML reading from the APP package. The simplest solution was, if a book has no cover, to copy the fallback cover image, from the APP package, into the book images folder and reference it from there.

    Displaying ampersands in book titles regressed. Now fixed.
